# 04 · 性能与质量基线（全部实测数字）

> 全部数字来自**同一台机器**：RTX 4060 Laptop 8 GB（24 SM，驱动 616.64）/ 31.6 GB 内存 / Windows 11 26200 / 引擎 sha256 `B232E501BD3F3203…`。
> 原始证据：[`evidence/key-measurements/`](../evidence/key-measurements/)。

## 1. 速度基线

| 指标                     | 实测                  | 口径                                                |
| ------------------------ | --------------------- | --------------------------------------------------- |
| decode（短上下文）       | **26.88 – 27.23 t/s** | C1：3.5k 提示 / 500 输出 / 贪心 / 丢首轮 / 3 次中位 |
| decode（写代码）         | **28.6 t/s**          | 一道"写函数 + 单测"的题（输出 386 token / 14.4 秒） |
| decode（长上下文）       | 21.5 – 27 t/s         | 3 万 – 14 万 token 材料                             |
| decode（长回答 8192）    | **27.4 t/s**          | 连续生成 8192 token                                 |
| prefill（短提示）        | **290 – 292 t/s**     | C1 口径                                             |
| prefill（长材料 3 万）   | **280 t/s**           | 17 针材料 29,770 token                              |
| prefill（长材料 25 万）  | **250.5 t/s**         | 252,862 token                                       |
| 单次输出 8192 token 耗时 | **299.9 秒**          | ≈5 分钟                                             |
| 冷启动到 HTTP 200        | **3.8 – 6.1 秒**      | 双击脚本 → 200                                      |

**历史最好值 vs 最新复跑**：292.7 / 27.4 → 290.9 / 26.9（差 0.6% / 2.1%，属环境与热状态噪声；同一批次里"长材料/满载"的大数字几乎逐位重合）。

**参考门线**：decode ≥ **20.1 t/s** 算达标（57.75 × 256/736 带宽折算）；本机 ≈ **134%**。
decode 已被显存带宽钉死（权重 5.95 GB ÷ 256 GB/s ≈ 23 t/s）——**换参数不会更快**。

## 2. 质量基线（17 针深度剖面）

| 配置                    | 结果      | 备注                         |
| ----------------------- | --------- | ---------------------------- |
| **retrieval（本方案）** | **17/17** | 两档配置各测一次，都是 17/17 |
| recency（对照）         | 12/17     | 漏中段，且会**编造**缺失编号 |

**剖面细节**（17 个深度，0.5% → 99.5%）：

```
A1@0%  A2@7%  A3@13% A4@19% A5@25% A6@31% A7@38% A8@44% A9@50%
A10@56% A11@62% A12@69% A13@75% A14@81% A15@87% A16@93% A17@100%   -> 17/17
```

材料 29,770 token · 输出 277 token · `finish=stop` · prefill 280.0–280.5 t/s · decode 21.5–21.6 t/s · 耗时 119 s。

## 3. 长上下文实测（本方案的核心卖点）

| 项                 | 实测                                                    |
| ------------------ | ------------------------------------------------------- |
| 一次灌入           | **252,862 token**（= ctx 262,144 的 **96.5%**）         |
| 深段检索           | 针埋在 **50% 深度（≈12.6 万 token 处）** → **逐字命中** |
| prefill 速度       | **250.5 t/s**                                           |
| 冷读耗时           | **1,010 秒（≈17 分钟）**                                |
| 满载显存           | **6,789 MiB**（8 GB 卡内）                              |
| 满载 host 私有内存 | **19.22 GB**（可用物理内存只剩 ~3.7–4.5 GB）            |
| 其它已验证长度     | 145,060 token（≈575 秒）也通过                          |

**怎么读这张表**：长上下文不是"免费"的——**冷读一次约 17 分钟**。但同一个前缀的后续提问会命中缓存（见 §5），所以"先喂一次、再多轮追问"是正确用法。

## 4. 长回答实测（跑满引擎上限）

| 客户端 `max_tokens`             | 实际输出  | `finish_reason`      | decode    | 耗时    |
| ------------------------------- | --------- | -------------------- | --------- | ------- |
| 4600（在 gen=4096 的配置下）    | **4,096** | length               | —         | —       |
| 8400                            | 6,404     | stop（模型自己写完） | —         | —       |
| 12000                           | **8,192** | **length**           | 27.37 t/s | 299.9 s |
| 8192（用"写 200 个函数"提示词） | **8,192** | **length**           | 26.99 t/s | 304.3 s |

**结论**：**8192 就是引擎上限**（由 `--kvmem-gen-reserve` 决定），客户端给再大也没用；模型多数情况下会自己写到 6.4k–7.6k 就结束，只有"明确要求写长"的任务才会顶到 8192。

## 5. 前缀缓存：最省时间的杠杆

| 场景                  | 第一次      | 第二次（同前缀）                              | 倍数     |
| --------------------- | ----------- | --------------------------------------------- | -------- |
| 5.3 万 token 代码材料 | **193.9 s** | **4.9 s**（只重算 517 token，`cache=52,539`） | **≈38×** |

**用法**：把材料放在提示的**同一位置**（别改前文），后面每轮只换末尾的问题 ⇒ "迭代改代码"场景提速几十倍。

## 6. 显存与内存账

### 6.1 显存（按 budget 扫描）

| `--kvmem-budget`    | 显存峰值      |
| ------------------- | ------------- |
| 8192                | 5,997 MiB     |
| 16384               | 6,349 MiB     |
| **32768（本方案）** | **6,659 MiB** |
| 65536               | 7,371 MiB     |

空闲实测：**6,557 – 6,595 MiB**；灌满 25 万 token：**6,789 MiB** ⇒ **上下文长度几乎不改变显存**。

### 6.2 内存（host 侧，才是上下文真正的成本）

| 状态                         | host 私有内存 | 可用物理内存         |
| ---------------------------- | ------------- | -------------------- |
| 默认 `cpu-gb 12`（不推荐）   | **19.59 GB**  | 仅 **2.0 GB** ← 危险 |
| 日常档 `cpu-gb 4` 空闲       | 12.23 GB      | 7.0 GB               |
| 长上下文档 `cpu-gb 6` 空闲   | 13.47 GB      | 8.1 GB               |
| 长上下文档灌满 252,862 token | **19.22 GB**  | **3.66 GB**          |

**结论**：`--kvmem-cpu-gb` 是**预占**语义（不是上限），**永远显式设小值**。

### 6.3 KV 池容量

| `cpu-gb` | `cpu_bytes` | `cpu_slots` | 折算 token  | 够不够                       |
| -------- | ----------- | ----------- | ----------- | ---------------------------- |
| 4        | 4 GiB       | 1,820       | **232,960** | 够 131,072；**不够 262,144** |
| 6        | 6 GiB       | 2,730       | **349,440** | 够 262,144（余量 33%）       |

## 7. 思考模式（可选能力）

| 强度 | 思考量（同一道题） | 说明 |
| ---- | ------------------ | ---- |
| 低   | 588 字符           | 最快 |
| 中   | 787 字符           | 默认 |
| 高   | 863 字符           | 最稳 |

实例：狼羊白菜过河（强度=中）→ 思考 **1,437 字符** + 答案 698 字符（7 步表格 + 逐步验证），全程 **49.7 秒**，正确。
**注意**：思考量**计入** 8192 输出上限，复杂题 + 高强度可能把答案挤掉。
