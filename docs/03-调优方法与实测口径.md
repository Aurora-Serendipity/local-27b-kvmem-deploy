# 03 · 调优方法与实测口径

> 这一篇是**方法**，不是结论。结论在 [04-性能与质量基线](04-性能与质量基线.md)。
> 如果只记一句话：**口径不写死，所有对比都是幻觉。**

## 1. 三条纪律

1. **先量测、后调参**。文档给的数字只当线索；每改一个参数都要在本机重新量。
2. **一次只改一个变量**，并记录"改前 / 改后"。否则你无法回答"这个旋钮到底有没有用"。
3. **改完要回测已通过的项**。改动常常悄悄破坏别的东西（本机实例：长回答会让后续长材料检索失灵）。

## 2. 速度计测口径（C1）

**口径定义**（照抄可用）：

| 项         | 取值                                                                         | 为什么                                              |
| ---------- | ---------------------------------------------------------------------------- | --------------------------------------------------- |
| 提示长度   | **≥1000 token**（本机用 900 词的清单 ≈ 3568 token）                          | 短提示的 prefill 读数**完全不可信**（见 §5 陷阱 1） |
| 输出长度   | **≥400 token**（本机用 500）                                                 | 短输出的 decode 会被首 token 开销污染               |
| 采样       | **贪心**（`temperature=0`）                                                  | 去掉采样随机性                                      |
| 预热       | **丢弃第 1 轮**                                                              | 排除首次加载/分配开销                               |
| 轮数       | **3 轮取中位**                                                               | 抗抖动                                              |
| 数据来源   | **只读引擎自报的 `timings`**（`prompt_per_second` / `predicted_per_second`） | 自己掐表会把排队、网络、客户端开销算进去            |
| 防缓存污染 | 每轮提示**加一个随机 nonce**，并断言 `usage.prompt_cache_hit_tokens == 0`    | 否则第二轮的"prefill"其实是缓存命中，数字虚高       |

**复现脚本**：[`tools/measure-c1.ps1`](../tools/measure-c1.ps1)

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\measure-c1.ps1 `
  -Port 18200 -Rounds 4 -Warmup 1 -OutTokens 500 -PromptWords 900 -Tag myrun
```

本机基准结果：**prefill 290–292 t/s、decode 26.9–27.2 t/s**（历史最好值 292.7 / 27.4）。

**参考门线**：decode ≥ 20.1 t/s 算达标（按显存带宽折算：57.75 × 256/736）。本机 ≈ 门线的 134%。

## 3. 质量仪器：17 针深度剖面

**为什么不能用"几根针"**：浅层针全过会给你**假安心**。本机实测同一材料同一配置下，"只看浅层"与"铺满深度"结论可以完全相反。

**仪器构造**（[`tools/profile-needle.ps1`](../tools/profile-needle.ps1)）：

1. 生成 ≈24,000 token 的代码式材料（默认实测 ≈29,770 token）；
2. 在 **17 个深度**埋入 17 个唯一编号：`0.5% / 6.69% / 12.88% / … / 99.5%`（均分）；
3. 一次请求，要求模型**列出全部 17 个编号**；
4. 判分：逐条比对回答里是否出现该编号（**精确串匹配**，不做语义宽容）。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\profile-needle.ps1 `
  -Port 18200 -TargetTokens 24000 -MaxTokens 400 `
  -Depths '0.005,0.0669,0.1288,0.1906,0.2525,0.3144,0.3763,0.4381,0.5,0.5619,0.6238,0.6856,0.7475,0.8094,0.8713,0.9331,0.995' `
  -Tag myprofile
```

**⚠️ 这个仪器自己的坑（务必知道）**：17 条编号需要 ≈280 输出 token。若 `-MaxTokens` 给得太小（脚本早期默认 160），列表会被**拦腰截断**，后面的针"缺失"其实是**没来得及输出**——本机因此得到过一次**假的 10/17**，把上限提到 400 立刻恢复 **17/17**。

**判分前必看两个字段**：`finish_reason`（必须是 `stop`）与 `out_tokens`（不能等于上限）。脚本现在会在撞上限时打印"结论无效"警告。

**本机结论**：`retrieval` **17/17** vs `recency` **12/17**（fail 的针集中在中后段，且 recency 会**编造**缺失编号）。

## 4. 扫参矩阵与结论

**方法**：固定其余变量，逐项扫描，每项都跑 C1 + 17 针（必要时加显存峰值）。

| 参数             | 取值                                | 结论                                                                                                                                                           |
| ---------------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `KVMEM_CPU_GB`   | 12 / **4** / **6**                  | **最要命的参数**。12 会**预占** ~19.6 GB 私有内存（机器只剩 2 GB）；4/6 分别给 232,960 / 349,440 token 的池子，且**性能无回退**                                |
| `KV_CTX`         | 65536 / **131072** / **262144**     | 只要求池子够大；**不改变速度、不改变显存**（显存 6.14–6.20 GB 基本不动）                                                                                       |
| `KVMEM_GEN`      | **8192** / 4096                     | 就是 `generation_limit`。设 4096 时"要 4600"的请求**恰好停在 4096**；8192 时引擎允许写到 8192                                                                  |
| `KVMEM_BUDGET`   | 8192 / 16384 / **32768** / 65536    | 显存随之 5997 / 6349 / **6659** / 7371 MiB；32768 是"长回答后问大文件仍能检索"的临界点；65536 只涨显存无收益                                                   |
| `KVMEM_GPU_R`    | **0.25** / 0.5                      | **是上限不是预占**：两者显存峰值完全相同（6349 MiB）⇒ 本负载下不生效，保持 0.25                                                                                |
| `KVMEM_METHOD`   | **retrieval** / recency             | 17 针 **17/17 vs 12/17** ⇒ 长材料必须 retrieval                                                                                                                |
| `KVMEM_SINK`     | **4096**                            | 必须**显著小于** budget；`sink=budget` 时长提示**每个请求都 500**（日志 `incoming block … was not placed on GPU`），而短请求仍 200（所以别用短请求验证这个坑） |
| `KV_DTYPE`       | **q4_0** / q8_0 / f16 / int8 / bf16 | ⚠️ `int8`/`bf16` **引擎不认**（`unsupported cache type`，直接起不来）；`q8_0` 质量无提升（仍 17/17）但显存 +320 MiB ⇒ 保持 q4_0                                |
| `KVMEM_BLOCK`    | **128** / 64                        | 64 时池槽翻倍但总容量不变，17 针仍 17/17 ⇒ 无差异，保持 128                                                                                                    |
| `KVMEM_QPOLICY`  | **user** / legacy                   | 无差异                                                                                                                                                         |
| `KV_UB` / `KV_B` | **128 / 512**                       | 质量档的取值；显存不炸                                                                                                                                         |
| `KV_PORT`        | **18200**                           | 换端口实测可用（18201 → 200）；⚠️ 聊天页里把端口写死，换端口要同步改                                                                                           |
| `--spec-type`    | **none**                            | 本档权重没有 MTP 层，`draft-mtp` 会让引擎 7 秒后自杀                                                                                                           |
| 思考开关         | **关**（默认）                      | 默认 `think=0`。开启后同题 14.4 s → 24.7 s；强度影响思考量：低 588 / 中 787 / 高 863 字符                                                                      |

## 5. 五个"测量陷阱"（每一个都真实坑过我）

1. **短提示的速度读数毫无意义**。17 token 提示测出 `prefill 26 t/s`，真实值 ~290（**差 11 倍**）。任何时候看到"prefill 只有几十"先怀疑提示太短。
2. **输出上限会伪装成质量退化**。17 针假 10/17 的真相是 `max_tokens=160` 截断（见 §3）。**先看 `finish_reason` / `out_tokens`**。
3. **前缀缓存会把 prefill 变成"假的快"**。同一份 5.3 万 token 材料第二次问：193.9 s → 4.9 s（38×）。这是**优点**，但计测时必须用 nonce 排除。
4. **会话污染**：先让它写一大段（如 8192 token），紧接着问大文件，深段检索会失灵——它答"文件里没有"，其实是没取到。`budget 32768` 在 5.3 万材料上能挡住，**14.5 万挡不住** ⇒ 大材料放会话第一问，或先重启引擎。
5. **别用"能跑起来"当验收**。就绪 ≠ 能推理 ≠ 长上下文可用 ≠ 长回答跑满。本方案的验收是四层：**HTTP 200 → 真推理 → 深段针命中 → 8192 跑满**。
