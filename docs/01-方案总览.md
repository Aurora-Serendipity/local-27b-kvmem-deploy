# 01 · 方案总览

## 1. 我们要解决的问题

**目标**：在一台**消费级 8 GB 显存笔记本**上，得到一个**可日常使用的本地大模型**，要求同时满足：

1. 模型足够大（27B 级），能胜任**代码问答与长材料理解**，不是玩具；
2. **长材料**：能一次读入十几万到 25 万 token 的代码库/文档并正确检索；
3. **长回答**：单次能连续输出 8000 token 级的长内容（完整模块、长文）；
4. **不牺牲速度**：decode 要明显高于"可用门线"，日常问答不能等；
5. **不动系统**：不改注册表、不改系统 PATH、不装 CUDA Toolkit、可随时停机归还资源；
6. **可分享、可复现**：别人能照着做，结论有证据。

**硬件约束**（决定了全部设计）：

- 显存 8 GB —— 27B 的三元量化权重（5.5 GB）已经吃掉大半，**留给 KV 缓存的空间很少**；
- 内存 31.6 GB —— 够，但**上下文越长越紧张**（25 万 token 时 host 侧要 19.2 GB）；
- 单卡单用户 —— 不需要并发，只需要"一次把一件事做透"。

## 2. 技术路线为什么是这条

| 选择                                                 | 为什么                                                                                                                                 |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **三元量化模型（1.75 bpw）**                         | 27B 参数压到 5.5 GB，才可能在 8 GB 卡上跑；三元量化在这个尺度上质量损失可接受                                                          |
| **llama.cpp 系引擎（GGUF）**                         | 单文件部署、自带 CUDA 运行库、OpenAI 兼容接口、无 Python 依赖树                                                                        |
| **KVMem 分层（GPU 工作集 + host 池）**               | **本方案的关键**：不把所有 KV 都塞进显存，而是"GPU 上只留一个有限工作集（budget）+ 其余放 host 内存池"，于是**上下文可以远超显存容量** |
| **检索式选块（retrieval）而不是只看最近（recency）** | 长材料下 recency 会漏中段还会编造；实测 17 针剖面 **retrieval 17/17 vs recency 12/17**                                                 |
| **单槽服务**                                         | 单用户场景不需要并发；单槽让显存/内存预算完全确定                                                                                      |

## 3. 方案由哪几部分组成

```
你的工作目录\
├─ pkg3-lowvram-llama-kvmem\pkg3-lowvram-llama-kvmem\   ← 交付包（引擎 + 权重 + 上游文档）
│   ├─ engine\llama-kvmem-server.exe                     （冻结件，sha256 校验）
│   ├─ model\Ternary-Bonsai-2-27B-PTQ1_0.gguf            （5.54 GiB）
│   ├─ model\Ternary-Bonsai-2-27B-mmproj-Q8_0.gguf       （视觉投影件，本方案不用）
│   └─ start-retrieval.bat / 自检-搬家.ps1 / SHA256SUMS.txt
│
└─ launchers\                                            ← 本仓库提供的工具层
    ├─ 一键启动-日常推荐.cmd / 一键启动-长上下文.cmd
    ├─ 一键停机-日常推荐.cmd / 一键停机-长上下文.cmd
    ├─ 状态检查.cmd
    ├─ start-engine.ps1 / stop-engine.ps1 / status.ps1   （真正的逻辑）
    ├─ 聊天.html                                          （离线单文件中文聊天页）
    └─ 使用手册-本地模型.md                                （给最终使用者）
```

**职责划分**：

- **交付包**＝不可变的"事实层"（引擎、权重、上游文档）；我们**一个字节都不改**，靠 sha256 保证。
- **工具层**＝我们做的"使用层"：把 13 个环境变量按两档配好、把启停做成一键、把模型包成能聊天和管历史的界面。
- **证据层**＝`evidence\`：每次实测的原始 JSON、机器可读回执、11 条与上游文档的分歧记录。

## 4. 关键设计决策（三件套）

KVMem 分层下有三个参数必须一起理解：

| 参数                  | 本方案取值 | 它决定什么                          | 设计理由                                                                                             |
| --------------------- | ---------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `--kvmem-budget`      | **32768**  | GPU 上保留的 KV 工作集大小          | 太小（8192）会导致"长回答之后问大文件"检索失灵；32768 能覆盖常见长材料；再大（65536）只涨显存无收益  |
| `--kvmem-sink-tokens` | **4096**   | 常驻开头段（不参与换出）            | 开头通常是系统提示/任务定义，必须常驻；但**必须显著小于 budget**，等于 budget 会让长提示每个请求 500 |
| `--kvmem-gen-reserve` | **8192**   | 为生成本身预留的空间 = 单次输出上限 | 决定"长回答能写多长"；它就是引擎的 `generation_limit`，客户端要更多也拿不到                          |

再加两条：**`--kvmem-cpu-gb` 决定 host 池容量**（4 GiB = 232,960 token；6 GiB = 349,440 token），**`--kvmem-method retrieval`** 决定长材料下能不能取到中段。

## 5. 能力边界（明确做不到的，别浪费时间）

| 想做                 | 结论                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| 投机解码 / MTP 加速  | ❌ 本档权重**没有 MTP 层**（引擎原文 `GGUF missing nextn / qwen35.nextn_predict_layers`），设了 7 秒后进程自杀 |
| 换微调档"少思考"     | ❌ 该权重不在本机（需另下独立包）；且上游实测它思考量 +71.9%、分数下降、更慢                                   |
| 读图片 / 视觉        | ⚠️ 未验证；8 GB 卡开 mmproj 会抢显存，要开得加 `--no-mmproj-offload`                                           |
| 1M 级上下文          | ❌ 需 ≈40 GB 内存，本机 31.6 GB；实测上限 262,144                                                              |
| 多路并发             | ❌ 单槽服务，一次一个请求                                                                                      |
| 换参数让 decode 更快 | ❌ decode 已被显存带宽钉死（5.95 GB ÷ 256 GB/s ≈ 23 t/s），要更快只能换引擎或换卡                              |

## 6. 与"直接用云端 API"的取舍

|          | 本方案（本地）                     | 云端 API      |
| -------- | ---------------------------------- | ------------- |
| 成本     | 0（电费之外）                      | 按 token 计费 |
| 隐私     | **内容不出本机**                   | 上传          |
| 速度     | 27 t/s（约 1000 汉字/分钟）        | 通常更快      |
| 能力     | 中等（27B 三元量化）               | 最强模型      |
| 长上下文 | 25 万 token，但**冷读要 ~17 分钟** | 秒级          |
| 离线     | ✅                                 | ❌            |

**结论**：这套方案适合"**隐私敏感 + 长材料一次性喂入 + 能接受冷读等待**"的场景（读代码库、读长文档、离线写代码）；不适合"高频短问答、要求秒回"的场景。
