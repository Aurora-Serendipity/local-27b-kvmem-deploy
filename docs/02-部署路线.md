# 02 · 部署路线（从零到可用）

> 每一步都给出**判据**（怎么算过）。判据不过就别往下走。

## 步骤总览

```
① 校验交付包 → ② 放置工具层 → ③ 选档启动 → ④ 三条就绪判据 → ⑤ 调用（聊天页 / curl / SDK）
→ ⑥ 停机归还资源 →（可选）⑦ 聊天页持久化与备份
```

## ① 校验交付包（别跳）

**做什么**：解压交付包，确认三个关键制品与清单一致。

```powershell
cd <交付包目录>            # 例如 D:\Local Model\pkg3-lowvram-llama-kvmem\pkg3-lowvram-llama-kvmem
.\自检-搬家.ps1            # 搬家/路径无关自检
Get-FileHash .\engine\llama-kvmem-server.exe -Algorithm SHA256
Get-FileHash .\model\Ternary-Bonsai-2-27B-PTQ1_0.gguf -Algorithm SHA256
```

**判据**：

- 自检脚本最后一行出现 `✅ 可搬运（路径无关）自检通过`，且 `FAIL=0`；
- 两个 sha256 与 `SHA256SUMS.txt` 中对应行**逐字节一致**。

**为什么重要**：引擎和权重是冻结件。只要有一个字节不同，"我测过的结论"就不再适用于你的机器。

## ② 放置工具层

**做什么**：把本仓库的 `launchers\` 放到**与交付包同级**的父目录，形成：

```
<父目录>\
├─ pkg3-lowvram-llama-kvmem\pkg3-lowvram-llama-kvmem\   ← 交付包
└─ launchers\                                            ← 工具层
```

**判据**：`launchers\start-engine.ps1` 里默认推导出的 `$Pkg` 指向真实存在的 `start-retrieval.bat`。

**目录结构不一样怎么办**：脚本已支持显式指定（留空则按上面的约定自动推导）：

```powershell
.\start-engine.ps1 -Profile daily -PkgPath 'D:\somewhere\pkg3-lowvram-llama-kvmem\pkg3-lowvram-llama-kvmem'
```

## ③ 选档启动

| 你的需求                            | 用哪个                                 |
| ----------------------------------- | -------------------------------------- |
| 日常问答、写代码、材料 ≤13 万 token | **日常推荐档** `一键启动-日常推荐.cmd` |
| 要一次读入 ≥13 万 token 的大材料    | **长上下文档** `一键启动-长上下文.cmd` |

双击即用。脚本会做四件事：

1. **拦重复启动**——本机实测同一端口能被两台引擎同时绑定且不报错，所以必须先检查；
2. **内存体检**——长上下文档在可用内存 < 10 GB 时给警告；
3. **设进程级环境变量**（只影响本次启动的进程，不动系统）；
4. **在新窗口启动引擎并轮询就绪**，就绪后**真发一次推理请求**确认不是"只开了个壳"。

**脚本实际设置的参数**（两档）：

```powershell
# 先把可能残留的旧变量清掉，避免"上档次的参数"串味
foreach ($k in 'KVMEM_CPU_GB','KV_CTX','KVMEM_GEN','KVMEM_BUDGET','KVMEM_GPU_R','KVMEM_TRACE') { Remove-Item "Env:$k" -ErrorAction SilentlyContinue }

# 日常推荐档
$env:KVMEM_CPU_GB=4; $env:KV_CTX=131072; $env:KVMEM_GEN=8192; $env:KVMEM_BUDGET=32768; $env:KVMEM_GPU_R=0.25
.\start-retrieval.bat

# 长上下文档
$env:KVMEM_CPU_GB=6; $env:KV_CTX=262144; $env:KVMEM_GEN=8192; $env:KVMEM_BUDGET=32768; $env:KVMEM_GPU_R=0.25
.\start-retrieval.bat
```

> 脚本另外设 `NINFER_AGENT=1`，作用只是让交付包的启动件结尾不 `pause`，**不改引擎行为**。

## ④ 三条就绪判据（都满足才算起来了）

1. 引擎窗口里出现 `llama-kvmem-server listening on http://127.0.0.1:18200 … spec=off`；
2. `curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:18200/v1/models` 返回 **200**（本机实测 **3.8 – 6.1 秒**）；
3. 引擎窗口里有 `KVMEM_TIERS cpu_bytes=… cpu_slots=…`——**证明 KV 分层真的生效**（不是回退成全 GPU）。

**本机实测的分层结果**（用来对照）：

| 档                   | `cpu_bytes`         | `cpu_slots` | 折算 token |
| -------------------- | ------------------- | ----------- | ---------- |
| 日常（cpu-gb 4）     | 4294967296（4 GiB） | **1820**    | 232,960    |
| 长上下文（cpu-gb 6） | 6442450944（6 GiB） | **2730**    | 349,440    |

> 槽是按 128 token/块算的：`cpu_slots × 128`。**池子必须 ≥ 你需要的上下文**，最好留 30% 余量——262,144 上下文用 4 GiB 池（232,960）是不够的，必须 6 GiB。

## ⑤ 调用（三种方式）

**A. 聊天页（推荐，零安装）**：双击 `launchers\聊天.html`。单文件、离线、中文界面，支持流式输出、思考模式、多会话、上下文压缩与备份落盘。

**B. curl / 任何 HTTP 客户端**：

```powershell
curl.exe -s http://127.0.0.1:18200/v1/chat/completions -H "Content-Type: application/json" `
  -d '{"model":"local","messages":[{"role":"user","content":"用 Python 写一个快速排序"}],"max_tokens":8192}'
```

**C. OpenAI SDK**（任何兼容客户端都能接）：

```python
from openai import OpenAI
c = OpenAI(base_url="http://127.0.0.1:18200/v1", api_key="not-needed")
r = c.chat.completions.create(model="local",
        messages=[{"role":"user","content":"解释这段代码"}], max_tokens=8192)
print(r.choices[0].message.content)
```

**接口要点**：

| 端点                        | 用途                                                   |
| --------------------------- | ------------------------------------------------------ |
| `POST /v1/chat/completions` | 对话/生成（主用）                                      |
| `GET /v1/models`            | 就绪检查（返回的 id 是文件名，但**请求里写 `local`**） |
| `GET /props`                | 查看当前生效参数（`n_ctx`、`generation_limit`）        |
| `GET /slots`                | 看当前槽状态（是否在忙、处理了多少 token）             |

- `"model"` **必填**，值写 `local`；
- **不需要 API key**（`/props` 里 `auth.enabled=false`）；
- **`max_tokens` 给足 8192**（引擎上限就是 8192，给少了会被客户端自己截断）；
- **单槽串行**：一次一个请求，脚本批量调用别并发。

## ⑥ 停机（把资源还回去）

双击 `一键停机-*.cmd`（两个停机脚本一样，停机不分档）。脚本会：

1. **按端口反查 PID** 杀进程（不按进程名乱杀，避免误伤别人的引擎）；
2. 按 **exe 精确路径**清理"端口已释放但进程还在占显存"的孤儿；
3. 关掉承载启动件的 `cmd.exe` 窗口壳（否则会停在"请按任意键继续"）；
4. **复查**：端口是否释放、显存是否回落、可用内存多少。

**判据**：`显存占用 ：0 MiB`、`残留进程 ：0 个`、可用内存回到 ~20 GB。

## ⑦ （可选）聊天页的持久化与备份

聊天页把对话存在**浏览器本地**（IndexedDB，失败自动退 localStorage）：

- 关标签、关浏览器、停引擎再启动，**历史都在**；移动/改名 `launchers\` 文件夹也不丢（`file://` 的存储是所有本地页面共享的）；
- 左侧列表可**新建 / 切换 / 改名 / 删除 / 搜索**；
- 三条备份路径：**「备份到文件夹」**（授权一次，之后每轮自动把对话写成 `<标题>__<id>.json`，并在改名后自动清理旧标题文件）、**「导出全部/导出当前」**（JSON 下载）、**「导入 JSON」**（换机器恢复）。
- ⚠️ **清浏览器数据会连历史一起清掉**——所以要么绑备份文件夹，要么定期导出。

## 常见偏差与处理

| 现象                                     | 原因                                                | 处理                                       |
| ---------------------------------------- | --------------------------------------------------- | ------------------------------------------ |
| 启动脚本说"已经有引擎在监听"             | 上次没停干净                                        | 先跑停机脚本再启动（**绝不要两台一起开**） |
| "在超时时间内没有等到 200"               | 内存不足 / 端口被占 / 包被移动                      | 看引擎窗口最后几行；跑 `状态检查.cmd`      |
| 每个请求都 500                           | `sink` / `budget` 被改坏                            | 用启动脚本（它设好了 4096 / 32768）        |
| 回答说到一半没了，`finish_reason=length` | 撞了 8192 输出上限                                  | 让它"接着写"，或分两次问                   |
| 问大文件答"文件里没有"                   | 会话污染（见 [docs/06](06-常见问题与排错.md) 坑 1） | 大文件放会话第一问，或先重启引擎           |

完整排错表见 [docs/06-常见问题与排错](06-常见问题与排错.md)。
