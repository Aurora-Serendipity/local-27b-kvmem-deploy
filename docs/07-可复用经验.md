# 07 · 可复用经验（换机器 / 换模型都照这套做）

> 这一篇是**方法论沉淀**：不解决"这台机器怎么用"，解决"**下次换一台机器、换一个模型，怎么不踩坑**"。括号里是本次部署的真实代价。

## 1. 十条最值钱的经验

1. **先量测、后调参；文档的数字只当线索，不当结论。**（本次逐条核对上游文档，记下 **11 条"文档这么说、实测不是"**——例如"质量档每请求 +1.9~3.5 s"在本机根本没出现，反而更快。）
2. **计测口径必须先写死，再谈快慢。** 固定口径＝**长提示（≥1k token）+ 长输出（≥400）+ 贪心 + 丢首轮 + 3 次取中位 + 只读引擎自报的 `timings`**。口径不写死，所有对比都是幻觉。
3. **绝不用短提示判断速度。**（17 token 提示测出 `prefill 26 t/s`，真实值 ~290——**差 11 倍**。这条单列，因为太容易上当。）
4. **质量要用"深度剖面"当仪器，不能用单点检查。**（浅层针全过会给你假安心；17 针铺满 0.5%→99.5% 才能暴露"中段失效"。本机 retrieval 17/17 vs recency 12/17，差距全在中后段。）
5. **一次只改一个变量，并记录"改前/改后"。**（否则你无法回答"这个旋钮到底有没有用"。）
6. **改了一个参数，要回测其它已通过的项。**（本机教训：长回答会污染后续长材料检索；把 `budget` 提到 32768 才在 5.3 万材料上挡住。）
7. **结果异常时，先怀疑仪器，再怀疑模型。**（本机实例：17 针跑出"10/17"，真相是**输出上限 160 token 把列表截断了**——提到 400 立刻 17/17。**先看 `finish_reason` / `out_tokens` 再下结论**。）
8. **"做不到"的清单比"能做到"更省时间。**（MTP/投机解码、微调档、视觉、1M 上下文——逐项验证并写死原因，避免以后反复试。）
9. **把结论落成文件，附上原始证据和校验和。**（每次实测留 JSON + 日志 + sha256；验证记录按轮次累加。没有证据的结论等于没有结论。）
10. **系统级配置一律不动。** 只设**进程级**环境变量（不改注册表、不改系统 PATH、不装驱动/依赖），停机后显存与内存完全归还——这让"试错"变成零风险动作。

## 2. Windows 上的四个"必踩"陷阱（血泪级别）

| 陷阱                       | 现象                                                                     | 正确做法                                                                             |
| -------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **`.cmd` 用非 ASCII**      | cmd 按 OEM 代码页解析，中文把命令切断，脚本行为诡异                      | `.cmd` **只用 ASCII**（连中文注释也别放），逻辑放进 `.ps1`                           |
| **`.ps1` 无 BOM 却含中文** | PowerShell 5.1 按 ANSI/GBK 读 → 乱码，甚至 `missing terminator` 解析失败 | 含中文的 `.ps1` **必须 UTF-8 带 BOM**；**改完要复查 BOM**（编辑器/工具可能悄悄去掉） |
| **按进程名杀进程**         | 误杀同名的别的实例                                                       | **按端口反查 PID**，或按 **exe 精确路径**清理孤儿                                    |
| **以为"端口被占会报错"**   | Windows 地址复用让**同一端口能被绑两次且不报错**，请求落到哪台不确定     | 启动脚本**自己拦重复启动**；换配置先停机                                             |

## 3. 资源账：显存 ≠ 内存，预占 ≠ 上限

- **上下文的成本在 host 内存，不在显存。**（ctx 从 131k 加到 262k，显存几乎不变，涨的是 host 私有内存——灌满 25 万 token 时到 **19.2 GB**，31.6 GB 机器只剩 ~3.7 GB 可用。）
- **"池大小"往往是预占，不是上限。**（本机 host KV 池默认值直接预占 ~18–19.6 GB，机器只剩 2 GB。**永远显式设小值**。）
- **给上下文留余量**：池子要 ≥ 上下文需求，且留 ~30%。（本机 4 GiB 池 = 232,960 token 够 131,072；要 262,144 必须 6 GiB = 349,440。）
- **先算带宽门线再期待速度**：`权重字节数 ÷ 显存带宽 ≈ decode 上限`。（本机 5.95 GB ÷ 256 GB/s ≈ 23 t/s，实测 27 t/s 已接近理论值 ⇒ **别再指望调参提速**。）

## 4. 应用层（聊天/客户端）最容易被忽略的三条

1. **摘要必须放在 `system` 消息里，模型才会当"自己的记忆"。**（实测：放 user 消息里问"我叫什么" → 3/3 答"你没提供"；改 system → 3/3 答对。压缩长对话时这条决定成败。）
2. **裁剪历史时，`system` 摘要要强制保留**，否则一裁剪模型立刻"失忆"。
3. **浏览器直连本机服务**：`file://` 页面能调 `http://127.0.0.1` 的前提是**服务端 CORS 放开**（本机引擎返回 `Access-Control-Allow-Origin: *`，所以离线单文件网页可以直接用）；另外 **`file://` 的本地存储是所有本地页面共享的**——网页挪目录/改名都不丢历史，但也意味着"清浏览器数据"会一起清掉。

## 5. 换模型时的检查清单

按顺序做，每步都要有数字：

1. **显存账**：权重大小 + KV 工作集（`budget`）能否塞进你的卡；
2. **内存账**：`cpu-gb` 池要覆盖目标上下文，且**别预占到机器没内存**；
3. **池容量核对**：`cpu_slots × 块大小 ≥ 目标 ctx`，留 30% 余量（看 `KVMEM_TIERS` 日志）；
4. **速度基线**：跑 C1（长提示 + 长输出 + 丢首轮 + 3 次中位）；
5. **质量剖面**：跑 17 针（记得给足 `max_tokens`，否则会假低分）；
6. **长上下文压测**：灌到目标长度的 95% 以上，验深段针；
7. **长回答上限**：用"明确要求写长"的提示词顶到 `gen-reserve`，确认 `finish=length`；
8. **污染检查**：先写长回答，再问大文件，看是否失灵（决定要不要"大文件放第一问"的规则）；
9. **记录**：把上面所有原始 JSON 存下来，附 sha256。

## 6. 分享给别人时的清单（本仓库就按这个来）

- **要带**：一键脚本、聊天页、使用手册、实测证据（JSON/回执）、可复现的测量脚本、版本与校验和、署名与上游链接。
- **不要带**：模型权重、引擎二进制、CUDA 运行库、任何**个人数据**（对话记录、备份目录、含用户名的路径与日志）。
- **必写**：上游出处与署名、已知限制、以及"哪些结论只在这台机器上成立"。
