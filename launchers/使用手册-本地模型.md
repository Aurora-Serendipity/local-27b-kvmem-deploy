# 📘 第一部分 · 新手入门（第一次用，只看这一节）

## 1.1 一句话搞懂这是什么

**本地模型 = 你电脑上的一个"离线版 AI 服务"。** 它平时是**关着的**，用之前要"开机"，用完"关机"。

- **不联网、不花钱、内容不出本机**（全部在你这台笔记本上算）；
- 它就是一个"聊天机器人 + 编程助手"，能力大约相当于一个中等规模的模型——够用来问代码、写脚本、读文档、改报错，别指望它跟云端最大的模型一样强；
- 它占资源：开机后吃约 **6.4 GB 显存 + 11 GB 内存**（关机就全还回来）。

就这一个概念，剩下都是细节。

## 1.2 第一次使用：照着做这一遍（约 3 分钟）

1. 打开文件夹 **`D:\Local Model\launchers`**
2. 双击 **`一键启动-日常推荐.cmd`**
   - 小窗口里出现 **`[就绪] HTTP 200`** 和 **`[自检] 真推理返回：OK`** → 模型起来了（约 4–10 秒）
   - 同时会另开一个窗口写着 `Bonsai-27B engine [...]` → **那是模型本体，别关它**
3. 回到同一个文件夹，双击 **`聊天.html`** → 浏览器打开聊天界面
4. 在下面输入框打字，**按回车**发送 → 答案会**一个字一个字冒出来**
5. 用完了：双击 **`一键停机-日常推荐.cmd`**（聊天页不用管，关掉浏览器标签即可）

> 哪一步看不懂：先双击 `状态检查.cmd`，它会告出"在不在跑、是哪档、显存内存多少、接口通不通、真推理行不行"。

## 1.3 你的三个真实场景

### 场景 A · 问代码 / 写代码（最常用）

启动**日常档** → 在 `聊天.html` 里问就行。写代码时建议把"风格"选成**精确**（结果更稳）。

- 例：把报错原文整段贴进去，问"这个错误怎么修"
- 例："用 Python 写一个 X，带注释和测试"

### 场景 B · 让它读一整个文件（长材料问答）

1. **先选档启动**：文件不大（10 万汉字以内）→ **日常档**；超大文件（十几万字以上）→ **`一键启动-长上下文.cmd`**
2. **怎么把文件给它**：记事本打开文件 → `Ctrl+A` → `Ctrl+C` → 粘到聊天框，**前面加一句**："下面是一个文件，请读完再回答我的问题：……"
3. ⚠️ **最重要的一条**：**大文件要放在这次对话的"第一个问题"**。
   先启动 → 先贴文件 → 先提问。若先让它写了一长段、再贴大文件，它可能答"文件里没有这个内容"（本机实测复现过；换文件前重新启动一次即可）

### 场景 C · 对着同一个文件反复追问（最省时间）

第一问把文件贴进去；**后面每一问只改最后那句话，不要重新贴文件、不要「＋新建对话」**（新建等于换一段上下文，模型就看不到前面那份材料了）。

- 实测：同一份 5.3 万 token 的材料，第一次要 194 秒，**第二次只要 5 秒**（引擎复用了前缀）。

## 1.4 日常就这四步

**启动 → 聊天 → 停机 →（不确定就跑 `状态检查.cmd`）**

1. **别改交付包里的任何文件**（尤其 `engine\`，那是冻结件，改了校验就不过）；

## 1. 两套配置怎么选

|                    | **日常推荐**                                                       | **长上下文**                                                            |
| ------------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 启动脚本           | `一键启动-日常推荐.cmd`                                            | `一键启动-长上下文.cmd`                                                 |
| 参数               | `cpu-gb 4 / ctx 131072 / gen 8192 / budget 32768 / gpu-ratio 0.25` | `cpu-gb 6 / ctx 262144 / gen 8192 / budget 32768 / gpu-ratio 0.25`      |
| 上下文上限         | 131,072 token                                                      | 262,144 token（实测灌到 **252,862** 仍能正确检索）                      |
| 显存               | ≈6.4 GB                                                            | ≈6.8 GB                                                                 |
| 内存               | ≈11 GB                                                             | ≈13 GB；**灌满 25 万 token 时约 19 GB**（那时机器可用内存只剩 ~3.7 GB） |
| 短提示速度（实测） | prefill 292.7 t/s、decode 27.4 t/s                                 | 292.9 / 27.5 t/s（**与日常档相同**）                                    |
| 什么时候用         | **默认就用它**：单文件、几万 token 的材料、日常问答、写代码        | 要一次读入 **≥13 万 token** 的大材料（超大代码库、长文档）              |

> **结论**：两档速度一样，长上下文档只是"能装更多 + 吃更多内存"。**没有 ≥13 万 token 的需求就永远用日常档。**

## 2. 启动 / 停机 / 状态

### 2.1 用脚本（推荐）

1. 双击 `一键启动-日常推荐.cmd`（或长上下文档）
2. 弹出的小窗口会告诉你：配置、预计占用、**是否就绪、真推理是否正常**
3. 同时会另开一个窗口（标题 `Bonsai-27B engine [...]`）——**那是引擎本体，别关它**
4. 关机/停用：双击 `一键停机-*.cmd`

脚本已经内置的保护：

- **不允许重复启动**：本机实测同一端口可以被两台引擎同时绑定（不会报错！），所以脚本会先检查，已在跑就直接拦下并告诉你当前配置。
- **长上下文档内存预警**：可用内存 < 10 GB 时会提醒你。
- **启动后自检**：不只是等端口，还会真发一次请求确认能推理。
- **停机后自动清理**：连引擎窗口一起关掉，不留"请按任意键继续"的僵尸窗口；并复查端口释放与显存回落。

### 2.2 手动命令（脚本坏了时用）

```powershell
cd "D:\Local Model\pkg3-lowvram-llama-kvmem\pkg3-lowvram-llama-kvmem"

# 先把可能残留的旧变量清掉（启动脚本也做这一步，避免"上档次的参数"串味）
foreach ($k in 'KVMEM_CPU_GB','KV_CTX','KVMEM_GEN','KVMEM_BUDGET','KVMEM_GPU_R','KVMEM_TRACE') { Remove-Item "Env:$k" -ErrorAction SilentlyContinue }

# 日常档
$env:KVMEM_CPU_GB=4; $env:KV_CTX=131072; $env:KVMEM_GEN=8192; $env:KVMEM_BUDGET=32768; $env:KVMEM_GPU_R=0.25
.\start-retrieval.bat

# 长上下文档
$env:KVMEM_CPU_GB=6; $env:KV_CTX=262144; $env:KVMEM_GEN=8192; $env:KVMEM_BUDGET=32768; $env:KVMEM_GPU_R=0.25
.\start-retrieval.bat

# 就绪判据（约 5 秒后）
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:18200/v1/models     # 期望 200

# 停机（按端口杀，不要按进程名杀）
$p=(Get-NetTCPConnection -LocalPort 18200 -State Listen).OwningProcess; Stop-Process -Id $p -Force
```

> 上面这 5 个变量就是两个启动脚本实际设的**全部**内容（脚本另外会设 `NINFER_AGENT=1`，作用只是让启动件结尾不 `pause`，不改引擎行为）。

### 2.3 就绪的三条判据（都满足才算起来了）

1. 引擎窗口里出现 `llama-kvmem-server listening on http://127.0.0.1:18200 … spec=off`
2. `curl` 上面那条命令返回 **200**（本机实测 4–10 秒）
3. 引擎窗口里有 `KVMEM_TIERS cpu_bytes=… cpu_slots=…`（证明 KV 分层生效）

## 3. 怎么调用（三种方式）

### 3.1 本地聊天页（推荐 · 零安装）

双击 **`聊天.html`**（就在 `launchers\` 里），浏览器会打开一个中文聊天界面：输入问题 → 回车 → 答案**逐字流式出现**。界面上的开关：

| 控件                                   | 作用                                                                                                                                                                         |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **左侧会话列表**                       | 所有对话自动保存（关标签/重启引擎都在）。可**新建 / 切换 / 改名 / 删除 / 搜索**（标题自动取第一句话）                                                                        |
| **先推理再答（思考）**                 | 勾上＝先输出思维链再给答案（详见 §5-S6）。思考过程显示在可折叠的「💭 思考过程」框里，答完自动收起                                                                            |
| **思考强度**                           | 勾上思考后出现：低（快）/ 中（默认）/ 高（稳）。实测同一题思考量 588 / 787 / 863 字                                                                                          |
| **风格**                               | 默认 / 精确（写代码用，temperature=0）/ 发散（temperature=1）                                                                                                                |
| **底部计量条**                         | 本会话 ≈用了多少 token / 上限（上限是从引擎 `/props` 读的真实 ctx，不是猜的）；超 60% 变黄、85% 变红                                                                         |
| **只带最近 N 轮（临时 · 不改历史）**   | **临时手段**：这次发送只带最近 N 轮给模型，**会话历史一条不动**，取消勾选立刻恢复。省时省钱，但那段旧内容**这次对模型是隐身的**。另外：`system` 摘要**永远保留**，不会被裁掉 |
| **压缩上下文（永久 · 摘要+原文存档）** | **永久手段**：把更早的对话交给**模型写摘要**存进会话，之后每轮都带着这份摘要；**原文进存档、可查看、可一键还原**（详见 §3.4）                                                |
| **已压缩原文（N）**                    | 点开查看被压缩的原文（只读），里面有「还原全部原文」按钮                                                                                                                     |
| 停止                                   | 中途掐断本次生成（已生成的部分保留）                                                                                                                                         |
| 导出当前 / 导出全部 / 导入 JSON        | 把对话存成 .json 文件 / 从文件读回来（备份、换机器用）                                                                                                                       |
| **备份到文件夹**                       | 选一个目录（只需授权一次），之后**每轮自动把对话落盘**成 `<标题>__<id>.json`；另有「从文件夹恢复」                                                                           |
| 右下角状态                             | 实时字数；完成后显示"用时 / 字数 / 思考字数 / decode t/s"                                                                                                                    |

### 3.2 curl / 任何 HTTP 客户端

```powershell
# PowerShell 写法
curl.exe -s http://127.0.0.1:18200/v1/chat/completions -H "Content-Type: application/json" `
  -d '{"model":"local","messages":[{"role":"user","content":"用 Python 写一个快速排序"}],"max_tokens":8192}'
```

```bat
REM cmd 写法（引号写法不同，别抄错）
curl.exe -s http://127.0.0.1:18200/v1/chat/completions -H "Content-Type: application/json" -d "{\"model\":\"local\",\"messages\":[{\"role\":\"user\",\"content\":\"你好\"}],\"max_tokens\":8192}"
```

接口清单：

| 端点                        | 用途                                                 |
| --------------------------- | ---------------------------------------------------- |
| `POST /v1/chat/completions` | 对话/生成（主用）                                    |
| `GET /v1/models`            | 就绪检查；返回的 id 是文件名，但**请求里写 `local`** |
| `GET /props`                | 查看当前生效参数（`n_ctx`、`generation_limit` 等）   |

**要点**

- `"model"` 字段**必须带**，值用 `local`（实测可用）。
- **不需要 API key**（`/props` 里 `auth.enabled=false`）；任何 OpenAI 兼容客户端都能接：`base_url=http://127.0.0.1:18200/v1`，`api_key` 随便填。
- **`max_tokens` 一定要给足 8192**（见第 4 节：引擎上限就是 8192，给少了会被客户端自己截断）。
- 服务是**单槽**的：一次只处理一个请求，脚本批量调用要**串行**，别并发。

### 3.3 Python（OpenAI SDK）

```python
from openai import OpenAI
c = OpenAI(base_url="http://127.0.0.1:18200/v1", api_key="not-needed")
r = c.chat.completions.create(model="local",
        messages=[{"role":"user","content":"解释一下这段代码"}], max_tokens=8192)
print(r.choices[0].message.content)
```

### 3.4 会话管理 · 备份 · 上下文压缩（详解）

#### 会话保存在哪、怎么切

- 每次问答都**立刻**写进浏览器的本地数据库（IndexedDB；个别浏览器不支持时自动退回 localStorage），**不联网、不上传**。
- 关标签、关浏览器、停引擎再启动，历史都在；**移动/改名 `launchers\` 文件夹也不丢**（实测：`file://` 的存储是所有本地页面共享的）。
- 左侧列表：`＋新建对话`、点条目切换、`✏️` 改名、`🗑` 删除、顶部搜索框（标题和内容都能搜）。
- 标题**自动取你的第一句话**，不满意就改名。

#### 三种备份手段（按需要选）

| 手段                 | 怎么做                                                                                                          | 适合                                       |
| -------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **自动落盘（推荐）** | 点「备份到文件夹」→ 选 `D:\Local Model\launchers\会话记录\`（只需授权一次）→ 之后每轮自动写 `<标题>__<id>.json` | 想用记事本看、想进文件备份、怕清浏览器数据 |
| **手动导出**         | 「导出当前」/「导出全部」→ 存到浏览器下载目录                                                                   | 临时备份 / 发给别人                        |
| **导入**             | 「导入 JSON」选文件 → 合并进列表（同 id 会自动换个新 id，不会覆盖）                                             | 换机器、恢复备份                           |

> 「从文件夹恢复」会把备份目录里**比当前新**的会话读回来（按 `updatedAt` 判断），不会覆盖更新的版本。
>
> ✅ **备份目录会自己清理**：文件名叫 `<标题>__<id>.json`，所以改名会产生"同 id、不同名"的新文件——**每次写盘后自动删掉同一会话的旧标题文件**（只删"文件名以 `__<该会话 id>.json` 结尾、且不是刚写入的那个"；别的会话、目录里其他文件一律不动）。写盘后状态栏会显示 `已备份 HH:MM（清理旧标题文件 N 个）`。

#### 上下文压缩（长对话的正确解法）

**先分清底部这两个控件，它们不是一回事**：

|              | 「只带最近 N 轮（临时 · 不改历史）」 | 「压缩上下文（永久 · 摘要+原文存档）」 |
| ------------ | ------------------------------------ | -------------------------------------- |
| 干了什么     | 发请求时**少发**几轮                 | 把更早内容**改写成摘要**存进会话       |
| 旧内容对模型 | **看不见**（隐身，但数据还在）       | **看得见**（通过摘要）                 |
| 生效范围     | 只影响这一次发送，取消勾选就恢复     | 永久生效，之后每轮都带着摘要           |
| 代价         | 免费、瞬间                           | 要调一次模型（几秒到几十秒）           |
| 什么时候用   | 临时救急：这次问的事只跟最近几轮有关 | 长对话长期用：想让它一直记得前面的事   |

一句话记法：**只带最近 N 轮＝少发；压缩上下文＝改写**。两者不冲突——压缩后即使勾着"只带最近 N 轮"，`system` 摘要也**永远带着**。

聊久了历史会变长，最终会超过上下文上限（日常档 131072）。**不要用"删掉旧消息"**——那样信息就真没了。用 **「压缩上下文（永久 · 摘要+原文存档）」**：

1. 设「压缩时保留最近 N 轮原文」（默认 4 轮）；
2. 点「压缩上下文」→ 确认 → 模型把**更早的内容**读一遍，写成一份**摘要**（保留事实、结论、代码/命令、报错原文、你的偏好、待办；丢掉寒暄和重复）；
3. 摘要替换掉那些旧消息，**原文一条不丢地存进「已压缩原文」**；
4. 随时点「已压缩原文（N）」查看只读原文，里面还有**「还原全部原文」**一键回退。

**实测记录（2026-10-05，本机、真浏览器）**：

- 压缩 3 轮后：≈324 → ≈269 token，原文 6 条存档，摘要质量好（准确抓住了"测试者身份 / 工作内容 / 数据结构 / 待决问题"）；
- 查看存档、还原原文都正常（还原后 10 条原文回来、摘要消失、计量条回到 324）。

⚠️ **一个踩过的坑，已修复（值得你知道）**：摘要若放在普通"用户消息"里，模型会把它当成**外部资料**而不是**自己的记忆**——问"我叫什么"它会答"你没有提供"（实测 3 次全错）。改成 **`system` 角色**的写法后 **3 次全对**。所以现在摘要以 system 消息开头；另外勾了「只带最近 N 轮」时，**摘要会被强制保留**（否则一裁剪模型立刻失忆）。

⚠️ 压缩**不一定每次都变短**：如果被压缩的内容本来就少，摘要（含说明头）可能比原文还长，界面会明确提示"这次没变短"。长对话才是它的主战场。

## 4. 参数速查表（每个参数实测结论）

| 参数             | 本机取值        | 它管什么               | 实测结论 / 改了会怎样                                                                                                                                                                                                   |
| ---------------- | --------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `KVMEM_CPU_GB`   | 4 / 6           | host 侧 KV 池大小      | **最要命的参数**。默认 12 会**预占** ~18 GB 内存（不是"上限"）→ 机器只剩 2 GB 可用。4 → 池 232,960 token；6 → 349,440 token（262144 上下文必须以 6 起）                                                                 |
| `KV_CTX`         | 131072 / 262144 | 逻辑上下文（吃 host）  | 实测 252,862 token 请求跑通；**改大不改变速度、不改变显存**，只要求池子够大                                                                                                                                             |
| `KVMEM_GEN`      | 8192            | 单次生成上限（含思考） | **引擎上限**：客户端要 12000 也停在 8192（`finish=length`）。设 4096 时，要 4600 的请求**恰好停在 4096**                                                                                                                |
| `KVMEM_BUDGET`   | 32768           | GPU 上的 KV 工作集     | 32768 能避免"长回答之后问大文件检索失灵"（见第 7 节坑 1）；再往上（65536）只涨显存无收益                                                                                                                                |
| `KVMEM_GPU_R`    | 0.25            | KV 放 GPU 的比例上限   | **是上限不是预占**：0.5 与 0.25 的显存峰值完全相同（6349 MiB），本负载下不生效                                                                                                                                          |
| `KVMEM_METHOD`   | retrieval       | 选块策略               | **长材料必须 retrieval**：官方口径 17 针剖面 retrieval **17/17** vs recency **12/17**（recency 会漏中段，还会编造内容）                                                                                                 |
| `KVMEM_SINK`     | 4096            | 常驻开头段             | 必须**显著小于** budget；等于 budget 时**长提示每个请求都 500**（日志 `incoming block … was not placed on GPU`）                                                                                                        |
| `KV_DTYPE`       | q4_0            | KV 精度                | ⚠️ **别照文档设 `int8`/`bf16`** —— 引擎只认 `f16/f32/q8_0/q5_0/q4_0`，设 int8 **直接起不来**。q8_0 实测质量无提升（17/17 一样）、显存 +320 MiB                                                                          |
| `KV_UB` / `KV_B` | 128 / 512       | 批大小                 | 质量档就是这么设的；实测显存不炸                                                                                                                                                                                        |
| `KV_PORT`        | 18200           | 端口                   | 换端口实测可用（18201 → 200）。⚠️ 但 **`聊天.html` 里把端口写死了**（`const API/PROPS = "http://127.0.0.1:18200/…"`，文件开头的 script 里）——换端口就得同步改那两行，否则聊天页连不上                                   |
| `KVMEM_BLOCK`    | 128             | KV 块大小              | 64 也试过：池槽翻倍但总量不变，17 针仍 17/17，无差异 ⇒ 保持 128                                                                                                                                                         |
| `KVMEM_QPOLICY`  | user            | 检索 query 策略        | `legacy` 实测与 user 无差异 ⇒ 保持默认                                                                                                                                                                                  |
| `--spec-type`    | none            | 投机解码               | 本档权重**没有 MTP 层**：设 `draft-mtp` 引擎 7 秒后自杀（`GGUF missing nextn / qwen35.nextn_predict_layers`）⇒ 只能 none                                                                                                |
| 思考开关         | 关（默认）      | 是否输出思维链         | 默认 `think=0`、`enable_thinking=false`，**本来就没有"过度思考"**。**聊天页已提供开关**（勾选「先推理再答（思考）」+ 强度低/中/高）；API 里对应 `"chat_template_kwargs":{"enable_thinking":true,"reasoning_effort":"low | medium | xhigh"}`。实测强度影响思考量：低 588 字 / 中 787 字 / 高 863 字（同一道题） |

## 5. 典型场景手册

### S1 · 问代码 / 写代码（最常用）

用**日常档**。实测：一道"写 Python 函数 + 单测"的题 → 输出 386 token，**decode 28.6 t/s，14 秒**出结果。
要点：`max_tokens` 写 8192；想要完整长模块（如"写 200 个函数"）实测能一路写到 **8192 token 才被上限截断**（约 5 分钟）。

### S2 · 让模型读一个大文件 / 大代码库

- 文件 ≤13 万 token：**日常档**就够；≥13 万：**长上下文档**。
- **务必把这个大材料放在会话的"第一个请求"**（原因见第 7 节坑 1）。
- 冷读一次的成本（实测）：5.3 万 token ≈ 3.3 分钟；14.5 万 token ≈ 9.5 分钟；25 万 token ≈ 17 分钟。

### S3 · 迭代改代码（同一份代码反复追问）★ 最省时间

**把代码放在提示的同一位置**（别改前文），第二次起引擎会命中**前缀缓存**：
实测同一份 5.3 万 token 材料再问一次 → **193.9 秒 → 4.9 秒（约 38×）**。
👉 工作方式：**一次性把文件贴进去 + 第一问；后面每一问只换末尾的问题**，别重贴代码。

### S4 · 要很长的回答

`max_tokens` 给 8192。实测输出 8192 token 用时 ~300 秒（decode 27.4 t/s）。超过 8192 会被引擎截断；要更长只能调大 `KVMEM_GEN`（会让工作集变小，需另测）。

### S5 · 脚本批量处理

单槽服务，**串行**发请求；每轮之间不用重启。同一个长前缀批量提问会持续命中缓存，很快。

### S6 · 想让它"想清楚再答"（思考模式）

**聊天页**：勾选右下角 **「先推理再答（思考）」**，旁边出现 **思考强度**（低/中/高，默认中），然后正常提问。

- 思考过程会先**流式**显示在一个可折叠的「💭 思考过程（N 字）」框里，答案随后流式出现在下面；答完后思考框自动收起（点标题能展开重看）。
- 什么时候值得开：数学/逻辑推理、多步算法设计、复杂排错、要求"先分析再给结论"；
  什么时候不用开：普通问答、改代码、写脚本——**不开更快**（同一道题：不思考 14.4 秒 → 思考 24.7 秒）。
- ⚠️ **思考内容也算在单次 8192 token 的输出上限里**：强度选"高"+ 问题复杂时，思考可能吃掉大半预算，导致答案被截断（`finish_reason=length`）。真被截断就让它"接着写"，或改选"低"。
- 本机实测（2026-10-05，真浏览器）：狼羊白菜题，强度"中" → 思考 **1437 字**、答案 698 字、全程 **49.7 秒**，过程和答案都正确。
- API 里等价写法：`"chat_template_kwargs":{"enable_thinking":true,"reasoning_effort":"low|medium|xhigh"}`；
  另外启动参数 `--reasoning-budget N` 可以硬性限制思考长度（N=0 立即结束、N>0 到 N 个 think token 强制收尾）。

### S7 · 觉得变慢了

先跑 `状态检查.cmd` 看是不是真在跑（会不会其实连的是别的服务、或正在用 CPU）。再对照第 9 节基线。**注意口径**：短提示（十几 token）的 prefill 数字没意义（实测能差 10 倍），要看长提示+长输出。

### S8 · 换配置

停机 → 启动另一档。**绝不要两台同时开**（同端口可双绑，请求落到哪台不确定）。

## 7. 已知坑（都是实测出来的，文档里没有的）

**坑 1 · 长回答之后问大文件，深段检索会失灵** ★最容易踩

- 现象：先让它写一大段（如 6,400 token），紧接着问一个 5 万+ token 的文件，它会回答"文件里没有这个函数"（其实是没取到，不是文件的问题）。
- 实测：基线配置和长上下文配置都会中；`budget 32768` 在 5.3 万材料上能挡住，**14.5 万材料挡不住**。
- 处置：**大文件放在会话第一个请求**；或换文件前重启引擎（停机→启动，几秒）。

**坑 2 · `KVMEM_CPU_GB` 默认值是"预占"不是"上限"**
文档说 host 占用约 5.5 GB，实测默认 12 GiB 时引擎私有内存 **19.6 GB**，31.6 GB 的机器只剩 2 GB 可用。所以**永远显式设 4 或 6**（启动脚本已经帮你设了）。

**坑 3 · `KV_DTYPE=int8/bf16` 会让引擎起不来**
文档（03 页）让你调 int8/bf16，但本档引擎只认 `f16|f32|q8_0|q5_0|q4_0`。照抄会看到 `unsupported cache type`。**保持 q4_0**。

**坑 4 · 同一端口能被两台引擎同时绑定**
实测第一台占着 18200，第二台照样打印 `listening on …18200` 并常驻（Windows 的地址复用行为）。所以你**不会看到"端口被占用"报错**，风险是请求落到哪台不确定。启动脚本已内置拦截。

**坑 5 · `--restart` 不存在**
排错篇症状 9 让你用 `--restart` 强制重启，实测本 build 没这个开关（`unknown flag: --restart`）。**要重启就停机再启动**。

**坑 6 · `sink = budget` 时长提示每个请求都 500**
实测：`sink=budget=8192` + 长提示 → 两次都 HTTP 500，日志 `prepare_working_set: incoming block 90 was not placed on GPU`；但 17 token 的短请求仍返回 200（所以别用短请求验证这个）。启动件有硬守卫（违规 exit 21/22）。

**坑 7 · 输出被"悄悄截断"**
超过 `KVMEM_GEN` 就停，响应里 `finish_reason=length`，不会有报错。看到 `length` 就是被截断，加大 `KVMEM_GEN` 或让回答短一点。

**坑 8 · 这台 build 的引擎对"短提示"读数极度不准**
17 token 提示能测出 26 t/s 的 prefill（真实值 ~290）。**判断快慢必须用长提示+长输出**。

**坑 9 · 路径必须纯 ASCII**
交付包路径含中文会让引擎报"系统找不到指定的路径"。当前路径 `D:\Local Model\pkg3-lowvram-llama-kvmem\…` 是纯 ASCII（空格没问题，实测可用）。

**坑 10 · 别改 `engine\` 里的任何文件**
那是冻结件，sha256 与清单一致（`自检-搬家.ps1` 会验）。要换版本请另存并记录 sha256。

**坑 11 · 清了浏览器数据，对话历史会一起没**
历史存在浏览器的本地存储里，所以：**清"网站数据/缓存"、用无痕窗口、换浏览器（Chrome ↔ Edge 各存各的）都会看不到历史**。
→ 对策：点「备份到文件夹」绑定 `launchers\会话记录\`（每轮自动落盘），或定期「导出全部」。需要时用「导入 JSON」/「从文件夹恢复」读回来。

**坑 12 · 同一会话开两个标签页同时改**
两边都能改，**以最后写入的那次为准**（后写覆盖先写）。页面之间会自动同步**列表**，但同一个会话的并发编辑无法合并。
→ 对策：一个会话只在一个标签页里编辑。

## 9. 性能基线（判断"是不是变慢了"）

| 指标               | 本机实测                                     | 口径                                            |
| ------------------ | -------------------------------------------- | ----------------------------------------------- |
| decode（短上下文） | **27.4–27.5 t/s**                            | 3.5k 提示 / 500 输出 / 贪心 / 丢首轮 / 3 次中位 |
| decode（写代码）   | **28.6 t/s**                                 | 一道代码题的实测                                |
| decode（长上下文） | 23–27 t/s                                    | 5 万–14 万 token 材料                           |
| prefill            | **292–294 t/s**（短）｜250–275 t/s（长材料） | 同上                                            |
| 长回答             | 8192 token ≈ 300 秒                          | decode 27.4 t/s                                 |
| 冷启动到 200       | **4–10 秒**                                  | 双击脚本到就绪                                  |
| 显存               | 6.4–6.8 GB（8 GB 卡内）                      | budget 32768                                    |

> 带宽折算门线（文档口径）：decode ≥ 57.75×(256/736) = **20.1 t/s 算达标**；本机 27.4 ≈ 达标线的 137%。
> **decode 已经被显存带宽钉死**（权重 5.95 GB ÷ 256 GB/s ≈ 23 t/s），换任何参数都不会显著更快；要更快只能换引擎（ninfer 档）或换卡。

## 13. 可复用经验（换机器 / 换模型都照这套做）

> 这一节是**方法论沉淀**，不是本机专属操作。前 12 节解决"这台机器怎么用"；这一节解决"**下次换一台机器、换一个模型，怎么不踩坑**"。括号里是本次部署里对应的真实代价。

### 13.1 十条最值钱的经验

1. **先量测、后调参；文档的数字只当线索，不当结论。**（本次逐条核对文档，记下 **11 条"文档这么说、实测不是"**——例如"质量档每请求 +1.9~3.5 s"在本机根本没出现。）
2. **计测口径必须先写死，再谈快慢。** 固定口径＝**长提示（≥1k token）+ 长输出（≥400）+ 贪心 + 丢首轮 + 3 次取中位 + 只读引擎自报的 `timings`**。口径不写死，所有对比都是幻觉。
3. **绝不用短提示判断速度。**（本机 17 token 提示测出 `prefill 26 t/s`，真实值 ~290——差 11 倍。这条单列，因为太容易上当。）
4. **质量要用"深度剖面"当仪器，不能用单点检查。**（浅层针全过会给你假安心；17 针铺满 0.5%→99.5% 才能暴露"中段失效"。本机 retrieval 17/17 vs recency 12/17，差距全在中后段。）
5. **一次只改一个变量，并记录"改前/改后"。**（扫参要能回答"这个旋钮到底有没有用"，否则只是随机游走。）
6. **改了一个参数，要回测其它已通过的项。**（本机教训：长回答会污染后续长材料检索；把 budget 提到 32768 才在 5.3 万材料上挡住。）
7. **结果异常时，先怀疑仪器，再怀疑模型。**（本机实例：17 针跑出"10/17"，真相是**输出上限 160 token 把列表截断了**——提到 400 立刻 17/17。**先看 `finish_reason` / `out_tokens` 再下结论**。）
8. **"做不到"的清单比"能做到"更省时间。**（MTP/投机、Swift 微调、视觉、1M 上下文——逐项验证并写死原因，避免以后反复试。）
9. **把结论落成文件，附上原始证据和校验和。**（每次实测留 JSON + 日志 + sha256；回执按轮次累加。没有证据的结论等于没有结论。）
10. **系统级配置一律不动。** 只设**进程级**环境变量（本次全程如此：不改注册表、不改系统 PATH、不装驱动/依赖），停机后显存与内存完全归还——这让"试错"变成零风险动作。

### 13.2 Windows 上的四个"必踩"陷阱（血泪级别）

| 陷阱                       | 现象                                                                     | 正确做法                                                                             |
| -------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| **`.cmd` 用非 ASCII**      | cmd 按 OEM 代码页解析，中文把命令切断，脚本行为诡异                      | `.cmd` **只用 ASCII**（连中文注释也别放），逻辑放进 `.ps1`                           |
| **`.ps1` 无 BOM 却含中文** | PowerShell 5.1 按 ANSI/GBK 读 → 乱码，甚至 `missing terminator` 解析失败 | 含中文的 `.ps1` **必须 UTF-8 带 BOM**；**改完要复查 BOM**（编辑器/工具可能悄悄去掉） |
| **按进程名杀进程**         | 误杀同名的别的实例                                                       | **按端口反查 PID**，或按 **exe 精确路径**清理孤儿                                    |
| **以为"端口被占会报错"**   | Windows 地址复用让**同一端口能被绑两次且不报错**，请求落到哪台不确定     | 启动脚本**自己拦重复启动**；换配置先停机                                             |

### 13.3 资源账：显存 ≠ 内存，预占 ≠ 上限

- **上下文的成本在 host 内存，不在显存。**（本机：ctx 从 131k 加到 262k，显存几乎不变，涨的是 host 私有内存——灌满 25 万 token 时到 **19.2 GB**，31.6 GB 的机器只剩 ~3.7 GB 可用。）
- **"池大小"往往是预占，不是上限。**（本机 host KV 池默认值直接预占 ~18~19.6 GB，机器只剩 2 GB。**永远显式设小值**，别被"上限"字样骗了。）
- **给上下文留余量**：池子要 ≥ 上下文需求，且留 ~30%。（本机 4 GiB 池 = 232,960 token，对 131,072 够用；要 262,144 必须 6 GiB = 349,440。）
- **分享时只带"能重建的东西"**：权重/引擎/CUDA 运行库都是大件且各有许可，**仓库里放脚本+文档+证据，大件给下载链接**。

### 13.4 应用层（聊天/客户端）最容易被忽略的三条

1. **摘要必须放在 `system` 消息里，模型才会当"自己的记忆"。**（实测：放 user 消息里问"我叫什么" → 3/3 答"你没提供"；改 system → 3/3 答对。压缩长对话时这条决定成败。）
2. **裁剪历史时，`system` 摘要要强制保留**，否则一裁剪模型立刻"失忆"。
3. **浏览器直连本机服务**：`file://` 页面能调 `http://127.0.0.1` 的前提是**服务端 CORS 放开**（本机引擎返回 `Access-Control-Allow-Origin: *`，所以离线单文件网页可直接用）；另外 **`file://` 的本地存储是所有本地页面共享的**——网页挪目录/改名都不丢历史，但也意味着"清浏览器数据"会一起清掉。

### 13.5 分享给别人时的清单（本次建 GitHub 仓库就按这个来）

- **要带**：一键脚本、聊天页、使用手册、实测证据（JSON/回执）、可复现的测量脚本、版本与校验和、署名与上游链接。
- **不要带**：模型权重、引擎二进制、CUDA 运行库、任何**个人数据**（对话记录、备份目录、含用户名的路径与日志）。
- **必写**：上游出处与署名（本次：_Created using Bonsai by Prism ML._；引擎血统 ninfer / PrismML-Eng 的 llama.cpp 分支）、已知限制、以及"哪些结论只在这台机器上成立"。
