# 8GB 显存笔记本跑 27B 大模型 · llama.cpp KVMem 分层部署实战

> **一句话**：在一台 **RTX 4060 Laptop 8 GB / 31.6 GB 内存 / Windows 11** 的笔记本上，用 **llama.cpp 的 KVMem 分层分支**跑通 **三元量化 27B 模型（1.75 bpw）**，并把它调成"能日常聊天写代码 + 能一次吃下 **25 万 token** 长材料 + 能输出 **8192 token** 长回答"的可用状态。
>
> 本仓库是**完整实测过**的方案：参数、数字、脚本、踩坑、证据，全部来自这台机器上的真实测量（不是照抄文档）。

## 1. 实测成果速览

| 指标               | 实测值                                                        | 说明                                                     |
| ------------------ | ------------------------------------------------------------- | -------------------------------------------------------- |
| **显存占用**       | **6.4 – 6.6 GB**（空闲）/ 6.79 GB（灌满 25 万 token）         | 8 GB 卡内；上下文学长几乎不涨显存                        |
| **内存占用**       | 11 GB（日常档）/ **19.2 GB**（25 万 token 灌满时）            | 上下文成本在 host 内存，不在显存                         |
| **冷启动到就绪**   | **3.8 – 6.1 秒**                                              | 双击脚本 → HTTP 200                                      |
| **短提示速度**     | prefill **291 t/s** · decode **26.9 – 27.2 t/s**              | C1 口径：3.5k 提示 / 500 输出 / 贪心 / 丢首轮 / 3 次中位 |
| **长材料 prefill** | 250 – 280 t/s                                                 | 25 万 token 材料 250.5 t/s；3 万 token 材料 280 t/s      |
| **最长上下文**     | **252,862 token**（= 262,144 的 96.5%）                       | 埋在 **50% 深度**（≈12.6 万 token 处）的针**逐字命中**   |
| **最长输出**       | **8192 token**（引擎上限）                                    | 要 12000 也只能到 8192；耗时 299.9 秒                    |
| **质量剖面**       | **17/17**（retrieval）/ 12/17（recency）                      | 17 个深度 0.5% → 99.5% 逐点检查                          |
| **前缀缓存收益**   | 同一份 5.3 万 token 材料再问：**193.9 秒 → 4.9 秒（约 38×）** | 迭代改代码的关键                                         |

**参考门线**：decode ≥ **20.1 t/s** 算达标（按显存带宽折算）；本机 26.9 ≈ 门线的 **134%**。decode 已被显存带宽钉死（5.95 GB 权重 ÷ 256 GB/s ≈ 23 t/s），**换参数不会再快**，要更快只能换引擎或换卡。

## 4. 快速开始（四步）

```text
① 取得交付包（引擎 + 权重 + 文档），解压到某个目录，例如 D:\Local Model\pkg3-lowvram-llama-kvmem\pkg3-lowvram-llama-kvmem\
② 把本仓库的 launchers\ 放到与它同级的父目录（脚本会自动推导包路径；也可用 -PkgPath 显式指定）
③ 双击 launchers\一键启动-日常推荐.cmd      → 看到 [就绪] HTTP 200 和 [自检] 真推理返回：OK
④ 双击 launchers\聊天.html                  → 浏览器里直接聊（或按 docs/02 用 curl / OpenAI SDK 调用）
```

用完双击 `一键停机-*.cmd`（脚本会按端口杀进程、清孤儿、复查显存与内存归还）。

> 任何一步不对：先双击 `状态检查.cmd`，它会告诉你"在不在跑、是哪档、显存内存多少、接口通不通、真推理行不行"。

## 5. 两档配置（本方案的核心结论）

|             | **日常推荐档**                                    | **长上下文档**                                    |
| ----------- | ------------------------------------------------- | ------------------------------------------------- |
| 适用        | 单文件、几万 token 材料、日常问答、写代码         | 一次读入 ≥13 万 token 的大材料                    |
| 关键参数    | `cpu-gb 4 / ctx 131072 / gen 8192 / budget 32768` | `cpu-gb 6 / ctx 262144 / gen 8192 / budget 32768` |
| host KV 池  | 1820 槽 = **232,960 token**                       | 2730 槽 = **349,440 token**（余量 33%）           |
| 显存 / 内存 | ≈6.4 GB / ≈11 GB                                  | ≈6.8 GB / ≈13 GB（灌满时 19.2 GB）                |
| 速度        | prefill 291 / decode 27 t/s                       | **与日常档相同**                                  |

**两档速度几乎一样**——长上下文档只是"能装更多 + 吃更多内存"。**没有 ≥13 万 token 的需求就永远用日常档。**

固定不变的参数（两档共用）：`retrieval` 选块 · `sink 4096` · `block 128` · `kv q4_0` · `gpu-ratio 0.25` · `ub 128 / b 512` · `spec none` · `gen-reserve 8192`。
每个参数的实测结论与"改了会怎样"见 **[docs/03](docs/03-调优方法与实测口径.md)** 与手册 §4。

## 6. 这套方案解决了哪些真问题（也是本仓库最值钱的部分）

部署本身不难；难的是**这些坑**——都是本机实测撞出来的：

1. **"上下文变长"吃的是内存不是显存**：ctx 翻倍显存几乎不动，host 私有内存涨到 19.2 GB。
2. **KV 池参数是"预占"不是"上限"**：默认值直接预占 ~18–19.6 GB，31.6 GB 机器只剩 2 GB 可用 ⇒ 必须显式设小值。
3. **长回答会污染后续长材料检索**：先让它写一大段，紧接着问大文件，它会答"文件里没有"（把 `budget` 提到 32768 能在 5.3 万材料上挡住；14.5 万挡不住 ⇒ 大材料放会话第一问，或先重启引擎）。
4. **短提示的速度读数是假的**：17 token 提示测出 `prefill 26 t/s`，真实值 ~290（差 11 倍）⇒ 必须用长提示 + 长输出计测。
5. **输出上限会伪装成"质量退化"**：17 针测试用默认 `max_tokens=160` 跑出"10/17"，真相是列表被截断；提到 400 立刻 17/17 ⇒ **先看 `finish_reason`**。
6. **同一端口能被两台引擎同时绑定且不报错**（Windows 地址复用）⇒ 启动脚本必须自己拦重复启动。
7. **压缩长对话时，摘要必须放在 `system` 消息里**：放 user 消息里，模型当"外部资料"，问"我叫什么"会答"你没提供"（实测 0/3 → 改后 3/3）。
8. **Windows 脚本编码**：`.cmd` 必须纯 ASCII；含中文的 `.ps1` 必须 UTF-8 带 BOM（否则 PS 5.1 按 GBK 读，直接解析失败）。

完整坑单（12 条）见 **[docs/06-常见问题与排错.md](docs/06-常见问题与排错.md)**；方法论沉淀见 **[docs/07-可复用经验.md](docs/07-可复用经验.md)**。

## 8. 已知限制（如实写）

- 所有数字来自**这一台机器**（RTX 4060 Laptop 8 GB / 31.6 GB / Win11）。换卡换内存，数字会变；**方法可复用，数字不可照搬**。
- **单槽服务**：一次只处理一个请求，脚本批量调用要串行。
- **不支持投机解码**：本档权重没有 MTP 层，设 `draft-mtp` 引擎 7 秒后自杀。
- **视觉/图片未验证**（8 GB 卡不建议开）。
- **1M 级上下文做不到**：需要 ≈40 GB 内存，本机上限 262,144。
- 文档里**11 条"上游文档这么说、本机实测不是"**的记录保留在 [evidence/回执](evidence/) 的 `contradictions` 字段中——我们按实测写，不替文档圆场。
